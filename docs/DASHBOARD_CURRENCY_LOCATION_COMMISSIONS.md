## Dashboard workspaces

Buyer and Seller are selected workspaces, not roles. The URL query state selects the visible workspace, while `/api/dashboard/access` and the role-scoped dashboard APIs derive seller eligibility and Store scope from the authenticated session/database. A buyer cannot acquire seller permissions by visiting `?mode=seller` or calling seller APIs. The separate admin surface is unchanged. Dashboard cart counts are refreshed from persisted cart data and the shared cart-change event.

## Currency and reference estimates

- The configured platform currency remains the actual charge currency. Checkout and subscription currency capabilities are distinct from display and Store pricing capabilities. Catalog activation cannot enable an unsupported provider currency. Store subscription billing is a separate Stripe Billing capability and remains disabled by default.
- Store base/listing currency and Store display offers are separate from provider payment connections. A reference-rate estimate does not change product/order charge amounts.
- USD is the legacy-compatible Store and demo-seed default. Migration 30 adds only missing USD Store offers and never overwrites an existing offer. Product and historical order rows are not rewritten. No old item-level currency snapshot is inferred from current deployment settings.
- Frankfurter v2 is the replaceable reference-rate adapter. Its documentation describes daily rates, multiple quote currencies, and errors for unsupported pairs; the application accepts only a returned and validated pair/date. No pair is assumed supported because it appears in the local catalog. The automatic refresh gate defaults off; an authorized admin refresh is available only when deployment configuration allows it.
- Automatic rates are usable only when both fetch time and source observation date are within the configured freshness window. Manual rates take precedence over Store-specific automatic rates; Store manual rates take precedence over global manual rates; a global manual rate takes precedence over automatic data. An absent/stale rate yields no estimate.
- Conversions use fixed-scale decimal rates and integer/rational minor-unit arithmetic with half-up rounding. A single cart never adds unlike charge currencies. At present the order charge remains the configured platform currency, and any storefront/cart conversion is explicitly an estimate with source date and fetch time.

## Location picker

The optional saved-address map uses Leaflet, a configurable `VITE_MAP_TILE_URL_TEMPLATE`, and visible OpenStreetMap attribution. It does not geocode or autocomplete. Browser geolocation is requested only after the user presses “Use my location”; users can enter the address manually or select a map point. Coordinates are saved only with the selected address. Tile services see viewport tile requests, not a geocoding query. Public community tile services are suitable only for low-volume development/testing, not a guaranteed production SLA; select an approved, appropriately hosted/contracted tile service before launch. Automated browser tests intercept tile traffic.

## Seller commission policy and ledger

Admin policy versions can target a Store or Store Plan version; a Store policy overrides the plan policy. Terms are effective-dated and snapshotted on each new seller order. A missing policy snapshots zero. Accrual is append-only and idempotent, and occurs only after verified online payment or after all seller shipments are fulfilled and an authorized COD collection transition marks the payment paid. Cancellation before collection does not accrue. Full verified refunds/chargebacks reverse remaining commission; provider events without reliable item allocation are held for admin review, and partial item allocations create compensating entries after balancing checks.

Migration `20261024000031_commission_refund_order_reconciliation` adds provider-object references, provider event times, original Stripe charge totals, and terminal-review reasons. Migration `20261024000032_webhook_event_lookup_identity` adds nullable payment lookup-reference and capture-assertion identity fields without rewriting historical events. Capture and refund/dispute processing uses a transaction-scoped provider-reference advisory lock followed by the parent-order lock. Processed-event persistence and all required seller/affiliate ledger and audit work commit in the same transaction; injected failures roll the event back and yield a retryable error. Exact duplicate payloads are idempotent, while same-ID payload changes to references or captured status are rejected. Stripe Checkout captures bind the PaymentIntent to the locally saved Checkout Session; earlier charge events remain explicitly unresolved until the same PaymentIntent appears on a verified capture, and a later replay retries association. Metadata alone never binds an event. Captured reconciliation validates the event currency/amount and handles Stripe cumulative refund snapshots by applying only the increase. Provider refund amounts are converted to proportional affiliate commission reversals over remaining eligible order base, with deterministic integer allocation. PayPal normalized-event handling uses the locally saved PayPal order reference; the database regression calls this internal verified-event processor with synthetic fixtures and does not exercise PayPal signature verification or contact PayPal. Unassociated/mismatched events are visible through the admin-only webhook-review endpoint. A full refund or dispute appends the remaining commission reversal and atomically marks open partial-allocation reviews `IGNORED` with a reason and system audit. Partial refund resolution still requires a captured payment (`paidAt`) and a verified source event; a full refund terminally supersedes unresolved reviews.

Migration `20261024000033_legacy_webhook_reconciliation` adds an explicit identity-verification marker and moves pre-reconciliation marketplace webhook rows with no stored event type into durable review. It excludes provider-event IDs referenced by wallet-funding audit history because the table is shared. A signed provider redelivery can reconcile such a row only after its event identity is checked and its provider references resolve unambiguously to a local payment; conflicting metadata, amounts, currencies, or payment state stay in review. Identity-unverified rows require provider redelivery; identity-verified pending rows can be retried through the admin-only, reason-audited reconciliation endpoint. Pending review responses are distinct from completed reconciliation responses. COD and POS affiliate settlement/audit now commit with the payment/order transaction, and cancellation plus its affiliate reversal commit under the parent-order lock. All affiliate reversal paths lock the parent order before stable ordered locks on earned ledger rows; retries are idempotent and adjustments are audited atomically. The fresh migration-upgrade, legacy replay, COD/POS failure-retry, and concurrent cancellation/refund regressions passed locally; see the current verification record below.

Seller commission statement totals are aggregated across the entire seller ledger independently of the 200-entry maximum display page and remain separated by currency. The UI derives `Accrued`, `Reversed`, or `Adjusted` from the immutable `entryType`; the schema does not have a mutable ledger `status` field.

This is a calculation/review ledger only. It does not establish who funds commission, collect seller deductions, fund seller payables, reconcile transfers, or initiate payouts. Amounts are not represented as payable funds. Those are separate product, legal, and accounting decisions. Stripe webhook fixtures are locally signed synthetic events; PayPal reconciliation fixtures are injected after the hypothetical signature-verification boundary. No real provider event, provider request, or live transaction was used in the tests.

## Final financial-safety remediation — 2026-10-24

Seller cancellation, online capture, seller-commission accrual/reversal, and affiliate settlement now serialize on the parent-order row before acquiring seller-order or ledger locks. Cancellation is terminal. Capture that follows cancellation still records the verified provider capture but places the event in review; cancelled seller orders are excluded from both commission ledgers. If capture commits first, a subsequent cancellation appends compensating seller and affiliate entries in the same transaction. Failed financial work rolls back with its payment/event and audit changes, allowing idempotent retry. A PostgreSQL concurrency regression covers cancellation-first and capture-first lock orderings and verifies that another order continues independently.

Migration `20261024000034_legacy_store_currency_backfill` is additive and follows migrations 28–33. The earlier pre-PR review stated that product creation used configured `CURRENCY`; inspection of the preceding source does not support that statement: product creation omitted the currency field and the then-current Product schema defaulted it to USD. Migration 34 derives each existing Store's base/listing currency from its persisted products to preserve imported or otherwise valid non-USD rows. It aborts before writes for mixed, inactive, uncatalogued, or non-Store-pricing currencies; it does not rewrite historical product/order/payment amounts. For a non-USD base, it disables checkout only on the exact generated migration-30 offer identity `legacy-usd-<storeId>`; explicit offers are preserved. Public currency availability and the order transaction both require the Store base currency to equal the configured platform charge currency, so a stale generated USD offer cannot authorize a charge. The upgrade regression starts at migration 27, distinguishes pre/post-migration state, covers generated and explicit offers, rejects mixed and unsupported catalog rows without changing Store/offer/product data, verifies public availability and checkout rejection, and preserves historical order/payment/item amounts.

The original empty Prisma `Schema engine error` remains unexplained and was not reproduced. The successful later migration deployment is not evidence that the original failure was fixed. The current remediation-specific verification is recorded above; older 34-migration results are historical and superseded by the current 35-migration run. An initial E2E setup attempt used inconsistent synthetic password-pepper values; the corrected seed and API process used the same test-only value and the full suite passed. No source or test assertion was changed for that setup issue.
