# Admin guide

The Platform team module also supports administrator-managed custom positions. Custom positions are reusable permission templates, separate from the immutable built-in positions listed below; editing a template does not silently change existing collaborators' grants. See `docs/PLATFORM_TEAM.md` for lifecycle and audit behavior.

The admin screen controls multi-vendor mode and independent Stripe, PayPal, PayMongo (PHP), Paystack (NGN), COD, and POS switches. A switch affects new sessions/transactions only; historical payments and webhook reconciliation remain addressable in the database.

Live shopping has two controls: deployment environment gate `LIVE_SHOPPING_AVAILABLE` and audited database setting `liveShoppingEnabled`. Both, plus provider readiness, must be true. The Control Center â†’ Marketplace â†’ Live shopping view shows readiness, scheduled sessions, and reports; admins can review/dismiss reports or terminate a session. The current repository has no selected provider, so enabling the admin setting correctly returns a readiness error rather than creating a fake stream. Disabling preserves sessions, reports, carts, and orders. Seller draft/scheduling is available before provider setup, but planned sessions remain private until all gates are healthy.

Turning multi-vendor mode off preserves sellers, products, orders, and history. It blocks new seller applications, seller product creation/sales, and mixed seller checkout while platform-owned products remain available. Re-enable the switch to restore eligible seller flows.

Seller decisions and setting changes are recorded in `AuditLog` with actor, timestamp, old/new values, and reason metadata when supplied. Review the audit endpoint after consequential changes.

## Platform administration control center

The `/admin/platform` area groups existing tools into Overview, Marketplace, Plans and billing, Payments, Growth, Members and security, Support and messaging, Integrations & APIs, Platform settings, and Governance. Orders/transactions, sellers, catalog taxonomy, Store Plans, seller payouts, affiliate controls, support tickets, branding, policies, availability/localization, provider configuration, payment-method switches, and audit history use server APIs. Items labeled Planned are informational and do not change settings. Club Coins remains on the separate `/admin/wallet` screen. See `docs/SUPPORT_MESSAGING.md` for ticket scope and safeguards.

Seller-managed shipping appears in Marketplace → Seller-managed shipping. Admins can inspect configured service labels, fees, zones, and enabled state, and can toggle global `sellerShippingEnabled`; this action is audited and does not edit a seller's settings or existing order snapshots. See `docs/SELLER_SHIPPING.md`. This is not carrier/API or shipping-label integration.

The Provider configurations page is a reference-only registry, not a credential editor or connectivity tester. It stores fixed environment-variable names or managed-secret references, shows masked values/readiness, and never returns secret values. No provider call is made. Provider configuration, buyer payment-method activation, Store Plan eligibility, seller-owned accounts, payouts, and wallet funding remain separate controls. Live configuration is fail-closed behind `LIVE_PROVIDER_CONFIGURATIONS_AVAILABLE`, default false. Live payment-method activation and live-mode checkout remain server-blocked in this increment because no provider verification has been implemented; local credential/mode presence is not verification. See [Integrations and payment methods](INTEGRATIONS_AND_PAYMENT_METHODS.md) for the context matrix, secret handling, archive behavior, and deferred prerequisites.

## Members and security

In Platform administration â†’ Members and security, admins can search/filter the member directory, inspect account role and status plus linked seller/store and activity counts, suspend or reactivate accounts, and revoke another member's sessions. Status changes and session revocations require an audit reason and are recorded in `AuditLog`. Suspension immediately revokes sessions and blocks subsequent authenticated requests and sign-ins. Suspending an approved seller also pauses that seller; reactivation restores seller approval only when the recorded suspension is still the reason the seller is suspended. The last active administrator cannot be suspended, and admins cannot suspend themselves or revoke their own sessions here. Account deletion, role changes/admin promotion, MFA management, and password resets are intentionally not provided by this module.

Platform administrators can add collaborators in Platform administration â†’ Members and security â†’ Platform team. Each account has a required work email, administrator-set initial password, position (Administrator, Supervisor, Accountant, Writer, or Editor), and individually editable module grants. Collaborators have a separate `PLATFORM_STAFF` role; even the Administrator position cannot create collaborators or promote itself to a full platform administrator. Email verification is required before staff API access. Permission changes revoke active sessions, disabled collaborators cannot sign in, and creation/access changes are audited with a required reason. Access is disabled rather than deleting the identity so its audit history remains intact. New password hashes use peppered pre-hashing to avoid bcrypt's 72-byte truncation; existing password hashes remain verifiable.

## Webhooks and API status

Platform administration â†’ Integrations & APIs â†’ Webhooks & API status checks the API process and database read latency, shows local runtime configuration readiness for the implemented Stripe, PayPal, PayMongo, and Paystack webhook endpoints, and lists recent inbound payment events with review/unverified filters. The event ledger refreshes every 15 seconds while open; verified supported payment events in review can be retried through the existing audited reconciliation workflow. A retry repeats internal matching only; it does not contact the provider or resend a webhook. “Configured” is not a provider-side delivery or connectivity verification, and this app does not yet retain HTTP delivery-attempt logs. Provider secret values remain in deployment configuration and are never returned by this screen.

## Platform and Store branding media

Platform administrators can draft and publish platform name/description, logo variants, favicon, default avatar, and social-sharing image in Platform administration → Platform settings → Branding. Seller owners and staff explicitly authorized for Store branding can edit that Store's logo, favicon, and banner in Store appearance. The controls accept PNG, JPEG, WebP, and GIF raster files, provide a local crop preview and focus controls, then normalize uploads to WebP on the server. Store favicon selection updates the public Store page and its published Store content pages; the platform favicon remains the fallback elsewhere. Device-only previews are not shared or considered published assets.

New public branding uploads require managed object storage (`CONTENT_OBJECT_STORAGE_AVAILABLE=true` plus bucket/region configuration) and use short-lived upload authorization; storage credentials never reach the browser. Store uploads reserve against the active Store Plan media quota. All completed uploads remain quarantined until a configured scanner approves them. Save-as-draft is allowed, but publish rejects pending/rejected media; the currently published image remains active when storage, verification, or scanning is unavailable. Public image delivery continues through `/content-media/:id`, which checks approval and a published reference. Private previews require the platform admin or the matching Store owner/explicitly authorized staff, respectively.

Store owners can grant or revoke the separate `canManageStoreBranding` staff permission. POS permission alone does not confer branding access. The permission defaults off and is added by migration `20261023000024_store_branding_staff_permission`; migration `20261023000025_store_favicon_media_guard` preflights existing logo, favicon, banner, avatar, and social-image references, then adds database guards for complete image type and tenant scope (including Store favicon references in the existing theme JSON), without adding columns or rewriting data. Reference checks and media-type changes use the same ordered transaction advisory locks. Use `npm run db:deploy` after backing up the target database. Removing an image clears the draft reference; it does not delete the stored asset. Publish the removal to change the public appearance. Local development without managed storage shows an actionable unavailable message and preserves the current public image. A functioning scanner remains an operational prerequisite; no scan is simulated by this UI.

## Durable media and scanner operations (2026-10-23)

New browser media flows use short-lived, object-scoped upload authorization; the browser uploads to managed storage without receiving storage credentials. The API re-reads the private object, checks the reservation, detects content, normalizes raster images, computes a SHA-256 checksum, and stores metadata only. Store uploads enforce the current plan quota and owner/staff scope. Migration `20261023000026_durable_media_scanning` adds purpose and idempotent scan-attempt state without rewriting existing references.

New files stay private until the configured ClamAV adapter returns a clean verdict. Configure `CONTENT_OBJECT_STORAGE_AVAILABLE`, `CONTENT_OBJECT_STORAGE_BUCKET`, `CONTENT_OBJECT_STORAGE_REGION` (and optional endpoint), plus `CONTENT_SCANNER_AVAILABLE`, `CONTENT_SCANNER_HOST`, `CONTENT_SCANNER_PORT`, and `CONTENT_SCANNER_TIMEOUT_MS`. The `clamd` TCP protocol is unauthenticated and unencrypted: expose it only on a trusted private network, restrict access to the API, and operate signature-update and health monitoring. Missing configuration, timeout, malformed response, malware result, and retries never create an approved state. Safe scan error codes and attempt metadata are persisted; duplicate and stale results are guarded by attempt identity. The current public avatar/branding stays active when a replacement is pending or rejected.

Defaults keep managed storage and scanner disabled. Local browser tests assert the unavailable state; database-backed API tests use synthetic storage and scanner fixtures only. No managed storage or ClamAV service was provisioned or contacted. Before enabling uploads in a hosted environment, configure private bucket CORS/lifecycle/backups, deployment credentials, ClamAV networking and signature operations, orphan retention, monitoring, and recovery procedures; then verify the real deployment end to end. The legacy `CONTENT_SCAN_REQUIRED` setting is not a way to bypass scanning.

## Platform email and SMTP

In Platform administration > Growth > Store Buster & email, administrators can independently configure, test, and activate SMTP for Mailtrap, Brevo, Gmail, SendGrid, Mailgun, Amazon SES, Postmark, SMTP2GO, Mailjet, MailerSend, Zoho Mail, Namecheap Private Email, or manual SMTP. Provider credentials are encrypted at rest, never returned to the browser, and audited without recording secrets. Each adapter test verifies the SMTP connection without sending an email; activation requires a successful test within 24 hours. Updating an active provider deactivates it until retested. Deployment variables `STORE_EMAIL_SMTP_HOST`, `STORE_EMAIL_SMTP_PORT`, `STORE_EMAIL_SMTP_SECURE`, `STORE_EMAIL_SMTP_REQUIRE_TLS`, paired `STORE_EMAIL_SMTP_USER`/`STORE_EMAIL_SMTP_PASSWORD`, `STORE_EMAIL_FROM`, and optional `STORE_EMAIL_REPLY_TO` remain supported as a fallback. TLS is required; configure SPF, DKIM, and DMARC with the mail provider.

Seller-owned SMTP is available separately to eligible paid Store Plans with email marketing enabled. It uses the shared provider directory (including Zoho Mail, Namecheap Private Email, and manual SMTP), store-scoped encrypted credentials, connection testing, and explicit activation. It is used only for that Store's opt-in newsletter confirmations and campaigns; platform transactional/account messages continue to use platform SMTP. The deployment marketing gate and unsubscribe-signing secret still apply. Seller custom-domain management uses a DNS TXT ownership proof plus the operator-configured `CUSTOM_DOMAIN_TARGET` CNAME. The hosting provider must independently route the hostname and issue HTTPS/TLS before the domain is used in public.

Account verification and transactional order/support/account notices use the active verified provider without the Store-marketing gate or marketing consent. Transactional notices are queued only for active accounts with a verified address and enabled category preferences; failed jobs retry with bounded backoff, and an administrator can requeue up to 500 failed jobs with an audit reason. Requeue is at-least-once and can duplicate messages after an ambiguous provider response. Seller marketing campaigns additionally require `STORE_EMAIL_TOKEN_SECRET` (at least 32 characters), `STORE_EMAIL_DELIVERY_AVAILABLE=true`, plan entitlement, double opt-in, and unsubscribe handling. No SMTP secrets are exposed in status responses. See `docs/EMAIL_AND_NOTIFICATIONS.md` and `docs/STORE_EMAIL_DELIVERY.md`.
