# Email and notifications

The growth schema provides durable in-app notifications, channel/category preferences, push-subscription registration, and an idempotent transactional email outbox. Order recording, shipment/receipt and order-resolution updates, support-ticket updates, and account reactivation notices persist their email jobs in the same database transaction as the in-app notification. Delivery re-checks the current account status, verified email address, and category preference immediately before sending. Jobs use bounded retries, stale-claim recovery, safe error codes, and an audited admin retry action for up to 500 failed jobs. Because SMTP acceptance and database commit cannot be made atomic, delivery is at-least-once and a retry after an ambiguous provider/network error can duplicate a message.

Transactional mail and account verification use the active platform SMTP provider after an admin verifies it. In Control Center → Store Buster & email, admins can independently save, test, and activate Mailtrap, Brevo, Gmail, SendGrid, Mailgun, Amazon SES, Postmark, SMTP2GO, Mailjet, MailerSend, or manual SMTP settings. These adapters use each provider's SMTP endpoint and credentials; REST-only APIs are not called. Credentials are AES-GCM encrypted at rest with a key derived from `PASSWORD_PEPPER`, are never returned to the dashboard, and a changed active configuration is automatically deactivated until it passes a fresh test and is activated. The previous deployment SMTP environment variables remain a fallback when no dashboard provider is active. Transactional notifications do not require the Store-marketing deployment gate, newsletter consent, or unsubscribe-token secret. The buyer Settings page allows category preferences for orders, support, and account-access notices; only active accounts with verified addresses are queued. Security verification emails are not preference-controlled. Notification reads, push subscriptions, and conversations remain authenticated and owner-scoped. Separately, Store email marketing has a provider-neutral SMTP delivery queue for double-opt-in subscribers and seller campaigns; it remains behind its own explicit deployment gate and plan/consent controls; see `STORE_EMAIL_DELIVERY.md`.

No SMTP credential, FCM project, or VAPID secret is committed or created. SMTP connection tests use `verify()` and send no message; successful tests expire after 24 hours. Marketing still requires the separate deployment unsubscribe-token secret, explicit marketing gate, a verified active provider, and applicable plan/consent checks. Account verification and transactional notifications require an active provider with host, sender, TLS, and recent verification but do not require marketing consent, the unsubscribe-signing secret, or the marketing gate. Transactional emails are queued only for events wired to the outbox; in-app/push/email delivery is not yet a universal fan-out for every notification event. The `ANDROID_PUSH` channel remains registration-only because no native Android application exists; compatible browser/PWA Web Push still needs owner-configured VAPID keys and a consent flow.

Before launch, configure a verified sender domain, provider bounce/complaint synchronization, retry/dead-letter monitoring, unsubscribe rules for marketing, and a secret store. The current SMTP marketing queue has bounded retries and manual suppression, but no automatic bounce/complaint webhook or inbox-delivery confirmation. Do not use marketing sends for transactional events and do not claim delivery merely because SMTP accepted a message.
