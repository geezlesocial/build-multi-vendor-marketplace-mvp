# Jima AI — local-first foundation

Jima is optional and does not participate in cart, checkout, payment, seller payout, or order decisions. It is disabled by default. An administrator can configure it under **Control center → Jima System AI**. Only loopback runtime URLs are accepted in this release, so chat content is not sent to a hosted provider. API configuration and knowledge edits are audited.

## Runtime and model

The adapter currently speaks Ollama's local `/api/chat` and `/api/tags` endpoints and disables Qwen3's separate reasoning output for concise user-facing replies. Ollama's repository is MIT-licensed ([license](https://github.com/ollama/ollama/blob/main/LICENSE)). `qwen3:0.6b` is the default for CPU-first local development; its Q4_K_M model is about 523 MB and its publisher lists Apache-2.0 ([model card](https://huggingface.co/Qwen/Qwen3-0.6B)). On one CPU-only development machine, a Jima-shaped prompt completed in 11.5 seconds and the authenticated chat route succeeded within its 20-second deadline. The 1.7B variant took 58.5 seconds on the same prompt shape and timed out through the app. Treat these as local smoke tests, not production performance guarantees; validate latency and answer quality on the deployment hardware and workload. Use the 1.7B or larger variant where latency and answer-quality testing support it.

Repository setup does not install Ollama or download model weights. Install Ollama using its official instructions and fetch an approved Qwen3 tag separately. Configure the local URL (normally `http://127.0.0.1:11434`) and exact installed model tag in the admin screen, save, then use **Test local runtime**. External/remote endpoints are intentionally rejected to reduce SSRF and accidental data egress. A production deployment needing a separate runtime host requires a reviewed private-network allowlist design before this restriction is relaxed.

## What works

- Administrators can inspect up to 30 validated configuration snapshots from the existing audit log and restore an earlier snapshot. Restore is append-only and creates a new audit event. Snapshots created before this feature do not contain full settings and are intentionally not offered as restorable versions. This uses the existing `AuditLog` model and requires no additional migration.
- Public `/api/ai/search?q=...` searches only approved products and stores owned by approved sellers.
- `/api/ai/recommendations` ranks approved, in-stock catalog items using configurable opted-in category relevance, listing freshness, and aggregate favorite counts. Admins set a result limit, per-store diversity cap, and homepage/product/store/widget placements. Category activity affects ranking only when both the user's personalization consent and the admin switch are enabled. Recommendations can be disabled per placement without disabling the rest of Jima.
- Authenticated chat persists user-owned conversations. It retrieves published help articles for `PUBLIC` and the signed-in buyer/seller audience, approved product and store matches, and a server-validated product/store page context when present. Responses include source links; help-source links reopen the published article through a role-checked endpoint. Retrieved text is treated as untrusted and the prompt prohibits unsupported transactional/policy claims. Runtime failure is an honest 503.
- Signed-in users can inspect their recent conversations, start a new one, delete an individual conversation, or delete all of their conversations. Server-side deletion filters by the authenticated owner. Administrators configure retention from 1 to 3650 days (30 by default); the API purges expired conversations hourly by last activity, including their messages.
- The widget is hidden when disabled, on admin and checkout pages, and clearly identifies the AI. Chat requires sign-in. To hand off, the user must explicitly consent to copying the recent conversation into a private support ticket. The handoff is idempotent per conversation, returns the existing ticket on retry, and staff respond through the existing support desk; the widget links to the user's support inbox.
- Admins can toggle AI/widget/personalization, choose model and generation limits, test the local runtime, and create/publish/unpublish help articles. Public and role-scoped article retrieval is enforced server-side, including direct article-source requests.

## SEO-FY Store and product audits

SEO-FY is an optional Store-plan feature at `/seller/seofy`. An administrator must explicitly include it in an eligible paid Store Plan version; it is off in legacy/platform defaults and all existing plan versions. Every audit, learning preference, and approval request rechecks an approved seller, that seller's own Store, the exact active paid subscription, and the plan entitlement on the server. Client-side visibility is not authorization. Seller dashboards never submit a Store ID to choose their tenant.

Audits inspect public Store or approved-product names/descriptions, approved product image/alt coverage, and optional basic metadata-length checks. If enabled, the existing loopback-only Jima runtime may draft only `seoTitle` and `seoDescription`. The response is schema-validated, rejects duplicate/unsupported fields and markup/control characters, and is shown as an unselected seller-review draft. No changes apply until the seller explicitly selects drafts and presses **Approve & apply selected**. The API rechecks entitlement and ownership, locks the Store and target row, and uses field compare-and-swap before applying. Stale drafts fail closed. SEO-FY cannot alter a slug, content body, price, stock, listing status, inventory, shipping, payment, ownership, roles, commissions, theme, or Store settings. Safe deterministic findings/drafts remain available when local Jima is disabled or unavailable; the UI states which path produced the report.

Only public catalog text and approved image-alt coverage are sent to the local runtime. Store or product text is framed as untrusted data; output is restricted to the metadata allowlist. Buyer identities, accounts, carts, orders, payments, and raw activity history are never included. Optional aggregate learning is off by default and requires separate seller opt-in, the admin-level Jima personalization switch, and the buyer's current personalization consent. It uses category aggregates from the preceding 90 days only when at least 20 distinct consenting users appear in a category; only counts/category labels reach Jima. It does not train or fine-tune a model, store raw activity in an SEO-FY report, or auto-apply edits. Turning it off does not modify buyer preferences. SEO-FY reports expire after 365 days; the cleanup worker runs hourly. Administrators see only aggregate service metrics, not individual sellers or report contents.

The metadata fields are publicly served on approved Store/product pages and update after seller approval. Search-engine crawling/indexing and ranking are external behaviors and are not guaranteed. No production Jima endpoint, hosted AI provider, external telemetry, or model training is enabled by this feature.

## Limits and safety

The assistant does not fetch private order, payment, refund, or seller-account details; it directs users to existing account/support workflows. It cannot execute marketplace actions. Search/recommendations are deterministic catalog operations, not LLM claims. Chat is limited to 12 requests per user per minute and at most two simultaneous local-runtime calls per API process; these in-memory controls are process-local and must move to shared infrastructure before horizontally scaling. Admins see aggregate successes/timeouts/unavailable outcomes for the last 24 hours; metrics contain no user IDs or chat text and hourly aggregates older than 30 days are pruned. Configuration history starts with saves made after the snapshot feature is available; older audit records lack full settings and cannot be restored. There is no vector database, embedding model, streaming, conversation export, raw-chat analytics, recommendation feedback, recommendation placements outside the endpoint, or dedicated support-agent assignment lifecycle in this slice. Do not treat this as production-ready until distributed abuse controls, accessibility review, model behavior, support notification, and deployment security are completed.

Database upgrades are forward-only Prisma migrations: `20261027170000_jima_ai_foundation` and `20261027183000_jima_operational_safeguards`. Apply them with the normal reviewed migration process; do not reset a database. The migrations add a JSON config field, user-owned conversation/message tables, approved-knowledge records, and content-free hourly runtime metrics.
